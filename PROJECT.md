## 1. Project Overview

**COSMOS** is a **LAN-first, offline-capable disaster response coordination platform**. It allows groups of people who are co-located on the same WiFi network or mobile hotspot to:

- **Chat** in a shared global chatroom in real time.
- **Mark locations** on a shared map by dropping pins with custom labels (e.g., "Need medical help", "Road blocked").

The critical design constraint is that **no internet connection is required**. Both map tiles and application assets are served locally from the backend. All communication happens within the LAN via WebSockets.

```
|                                                          |
|  +-------------+   HTTP/WebSocket   +----------------+  |
|  |   Client A  | <----------------> |                |  |
|  |  (Browser)  |                    |  Node.js       |  |
|  +-------------+                    |  Server        |  |

|  +-------------+                    +----------------+  |
|                                            |             |
|                                  +---------+---------+   |
|                                  |  Local Filesystem |   |
|                                  |  - React dist/    |   |
|                                  |  - Map tiles/     |   |
|                                  +-------------------+   |
```

**The server acts as both a web server and a WebSocket broker:**
- Serves the compiled React frontend SPA as static files.
- Serves pre-downloaded map tiles as static files from the `/tiles` route.
- Relays real-time messages (chat, pins) between connected clients via Socket.io.
- Maintains in-memory state for chat history and map pins.

**Static file serving (lines 27-31):**

The frontend dist path `../../frontend/cosmos/dist` is relative to `backend/dist/index.js` (compiled output location), navigating up to the project root.

**Socket.io CORS (lines 35-40):**
```typescript

```
Wildcard origin is intentional — required for LAN clients on different IP addresses.

**Connection handler (lines 42-91):**
On each new client connection:
1. Reads `socket.handshake.query.name` for the username.
2. Immediately emits `chat-history` and `pins-history` to the new client.
3. Registers event handlers for: `request-chat-history`, `request-pins-history`, `user-message`, `add-pin`, `disconnect`.

**Catch-all route (line 94):**

Enables React Router client-side routing. Must be registered AFTER Socket.io setup. Without this, refreshing on `/map` or `/chat` returns a 404.

**Startup banner (lines 98-122):**
Detects the machine's non-loopback IPv4 address via `os.networkInterfaces()` and prints both `localhost` and LAN `Network` URLs.

### 5.4 socket.ts — Singleton Socket Client

```typescript
const name = localStorage.getItem('chat-username') || 'Anonymous'
export const socket = io({ query: { name }, autoConnect: true })
```
- Evaluated **once** when first imported. The socket instance is shared across all components.
- The username is read from `localStorage` at module load time.
- Components that need a specific username update `socket.io.opts.query = { name: username }` before connecting.
- `autoConnect: true` initiates connection immediately on module load. However, `Chat` calls `socket.connect()` manually after registering listeners to avoid race conditions.

### 5.6 Chat.tsx — Most Complex Component (~224 lines)

**Local State:**
| State       | Type        | Purpose                                             |
|-------------|-------------|-----------------------------------------------------|
| username    | string      | Read from localStorage. Controls which screen shows.|
| joined      | boolean     | Guards join screen vs chat screen.                  |
| inputName   | string      | Controlled input for name entry.                    |
| message     | string      | Controlled input for message typing.                |
| messages    | Message[]   | Array of all messages to display.                   |
| connected   | boolean     | Mirrors socket connection state for UI feedback.    |

**Two-Screen Architecture:**
- **Join Screen**: Shown when `!joined && !username`. User enters a name, clicks "Enter Chat".
- **Chat Screen**: Full chat UI shown after joining.

**useEffect — Socket Setup (re-runs when `username` changes):**
- Short-circuits with `return` if `username` is empty.
- Updates socket query params.
- Registers listeners: `connect`, `disconnect`, `chat-history`, `server-message`.
- Emits `request-chat-history` (pulls current history explicitly).
- Calls `socket.connect()` if not already connected.
- Cleanup removes all four listeners on unmount.

**useEffect — Auto-scroll (re-runs when `messages` changes):**
- Calls `bottomRef.current?.scrollIntoView({ behavior: 'smooth' })` after every update.

**handleJoin():**
1. Trims and validates `inputName`.
2. Saves to `localStorage`.
3. Adds local System message ("You joined as...").
4. Sets `username` state — triggers the socket useEffect.

**handleSend():**
1. Validates text non-empty and socket connected.
2. Appends to local messages with `self: true` (optimistic update).
3. Emits `user-message` to server.
4. Clears input.

**Message Bubble Styling:**
- `self: true` -> right-aligned, cream (#FFFDD0) background.
- `name === 'System'` -> italic, subtle/muted style.
- All other -> left-aligned, dark background, sender name shown above.

### 5.7 Map.tsx

- Uses Leaflet's `useMapEvents` hook.

**Map component:**

## 6. Real-Time Communication Protocol (Socket.io Events)

All payloads are plain JSON. The server uses the default Socket.io namespace (`/`).

### Client -> Server Events

| Event                  | Payload                                       | Description                         |
|------------------------|-----------------------------------------------|-------------------------------------|
| user-message             | `{ message: string }`                         | Send a chat message                 |
| add-pin                  | `{ lat: number, lng: number, label: string }` | Drop a new map pin                  |
| request-chat-history     | (none)                                        | Pull full chat history from server  |
| request-pins-history     | (none)                                        | Pull full pins array from server    |
| request-requests-history | (none)                                        | Pull full requests array            |
| create-request           | `Partial<DisasterRequest>`                    | Create a new disaster request       |
| update-request           | `{ id: string, updates: Partial<...> }`       | Modify an existing request          |

### Server -> Client Events

| Event          | Payload         | Who Receives           | Description                                  |
|----------------|-----------------|------------------------|----------------------------------------------|
| chat-history    | ChatMessage[]    | Requesting client only | Full chat history on connect or request       |
| pins-history    | Pin[]            | Requesting client only | Full pins array on connect or request         |
| server-message  | ChatMessage      | All EXCEPT sender      | A new chat message from another user          |
| pin-added       | Pin              | ALL clients            | A new pin (including the client who placed it)|
| requests-history| DisasterRequest[]| Requesting client only | Full requests array on connect or request     |
| request-created | DisasterRequest  | ALL clients            | A new request has been added                  |
| request-updated | DisasterRequest  | ALL clients            | An existing request has been updated          |

> NOTE: Chat uses `socket.broadcast.emit` (excludes sender) because the sender adds the message locally via optimistic update. Pins use `io.emit` (all clients) because Map has no local optimistic update.

## 8. Business Logic & Lifecycles

### 8.1 Priority Assignment Rules
When a request is created, it is assigned a `basePriority` based on its category:
- **Priority 1 (Critical)**: `medical`, `rescue`
- **Priority 2 (Urgent)**: `medicine`
- **Priority 3 (High)**: `water`, `food`, `shelter`
- **Priority 4 (Medium)**: `sanitation`, `transport`
- **Priority 5 (Low)**: `information`

### 8.2 Time-Based Escalation Algorithm
The backend runs a `setInterval` loop every 60 seconds to evaluate all active requests:
1. **Aging**: If a request remains unresolved for > 60 minutes, its `priority` decreases numerically by 1 (e.g., Priority 3 -> Priority 2). If unresolved for > 120 minutes, it decreases by an additional 1.
2. **Cap**: Auto-escalation is strictly capped at Priority 1 (Critical).
3. **Exclusion**: Requests with a base priority of 5 (Low) are explicitly excluded from auto-escalating to avoid spamming the emergency channels with non-critical information.

### 8.3 Request Expiry
- Requests can be assigned an `expiresAt` timestamp (default: 24 hours).
- The evaluation loop marks requests as `expired` once `Date.now() > expiresAt`.
- Expired requests stop auto-escalating and disappear from the active 'Needs Help' list, but can be manually renewed by the original requester.

### 8.4 Request-Resource Matching
The frontend utilizes a local Haversine distance calculator (`utils.ts`) to match Requests to Nearby Resources:
- **Relevance**: Mapped directly from Category to Resource Type (e.g., `medical -> ['HOSPITAL', 'CLINIC', 'PHARMACY']`).
- **Sorting**: Matches are surfaced in the Request Card based on Availability (`OPEN` > `LIMITED`), Relevance, Distance, and Verification Age.

### 8.5 In-Memory & Persistent State (Backend)
- **Users**: Persisted to `backend/data/cosmos.json` (pure JSON file store). Tracks identity across restarts.
- **Resources**: Loaded statically from `backend/data/resources.json` on startup. Modifying status mutates memory but does *not* write back to JSON yet.
- **Requests & Chat**: In-memory only. Restarting the server clears these arrays.

## 9. Map & Tile System

Map tiles follow the standard XYZ tile convention:
```
backend/tiles/{zoom}/{x}/{y}.png
```

Available zoom levels: **11 to 16**.

Tiles are served by Express at `/tiles/*` and consumed by the Leaflet TileLayer:
```
http://${window.location.hostname}:3001/tiles/{z}/{x}/{y}.png
```

Key points:
- `window.location.hostname` is dynamic — always resolves to the same host serving the page.
- Port is hardcoded to `3001`. If changed in `.env`, this line in `Map.tsx` must also be updated.
- `errorTileUrl=""` suppresses broken-image errors for tiles outside the downloaded area.
- Default map center `[12.9109, 77.5223]` is a specific area in Bangalore, India — the tile set should cover this region.

## 13. Key Design Decisions & Constraints

1. **Offline-first**: No CDN, no external API calls. All assets served locally.
2. **Hybrid persistence**: Users are persisted using a local JSON file (`backend/data/cosmos.json`) to track identity and location across restarts without triggering native module issues in `pkg`. Chat/Pins remain in-memory for simplicity.
3. **Single backend file**: Core server logic in one `index.ts`, with DB interactions in `db.ts`.
4. **Username via query param**: Socket handshake carries the name — no auth flow needed.
5. **Optimistic chat updates**: Messages appear instantly without waiting for server ack. Server only broadcasts to others.
6. **Tiles hardcoded to port 3001**: Coupling point — must update `Map.tsx` if backend port changes.
7. **Map center hardcoded to Bangalore**: If deploying elsewhere, update both tile files and the default center coordinate.
8. **socket.ts singleton**: One shared socket across all components. `socket.off()` cleanup must be precise to avoid removing sibling component listeners.
9. **History re-requests on mount**: Both `Chat` and `Map` explicitly emit history request events on mount to handle component remount cases.

## 15. Unimplemented Features (For Next Phases)

As of Phase 08, the following aspects of a full disaster response platform are **NOT YET IMPLEMENTED**:
1. **Offline PWA / Service Workers**: While the app doesn't require an internet connection, clients must still reach the server on the LAN. The frontend is not configured as a true PWA that caches itself for when the LAN drops completely.
2. **Database Persistence for Requests/Chat**: `cosmos.json` only stores Users. Requests and Chat are lost if the Node server restarts.
3. **Resource State Persistence**: Modifying a resource's status mutates the in-memory array, but does not overwrite `resources.json`.
4. **Deleting Requests**: There is no UI or backend logic to actually *delete* a request, only to cancel or resolve it.
5. **Authentication**: Users choose their own usernames and UUIDs via `localStorage`. There is no password auth, meaning user spoofing on the open LAN is technically possible.
